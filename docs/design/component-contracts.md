# UI component contracts

Normative companion to [design-language.md](design-language.md). These are roles, not claims that types with these names already exist. Before implementing, locate the existing shared component and map its source path to the role in the change description. Extend it when appropriate; do not create a parallel component for one screen's cosmetic preference.

| Role | Contract | Avoid |
| --- | --- | --- |
| Settings field row | Stable label/value alignment, accessible name, editable content left-aligned, inline validation and preserved draft (`SettingsFieldRow`, see Settings pane building blocks) | Placeholder as the only label; hidden required setup |
| Section | Clear heading and related content; spacing first, container only when semantically useful (`SettingsSection` in Settings) | Card for every heading |
| Empty state | Explain absence and offer the next relevant action | Reporting backend failure as no data |
| Error state | Name failure, affected scope, data preservation and recovery | Log-only failure; generic Retry when input must change |
| Activity/status | Scope, operation, freshness, truthful progress/outcome; details reachable | Contradictory duplicate badges; indefinite unexplained spinner |
| Toolbar action | Native control, command identity, help, accessible label, keyboard equivalent where appropriate | Decorative tint; unclear disabled state |
| Citation | Stable source/range identity, readable label, deterministic destination, deduplication and path disambiguation | Breaking inline code; identical ambiguous chips |
| Approval card | Target, operation, scope, consequences and distinct allow/decline options | Unexplained session scope or 'safe' claims |
| Change review | Full review path, changed-file scope, unsaved/disk semantics, separate reject/close/apply outcomes | Applying unseen truncated content without a full review route |
| Composer | Draft preserved, send/stop state, clear attachments/context, focus, meaningful read-only state | Enabled-looking controls that silently do nothing |
| Selection menu | Current selection marked, short readable labels, optional secondary detail | Redundant slider/badge/picker for the same discrete value |
| Inline banner | `InlineBanner` (`desktop/Views/Main/InlineBanner.swift`): icon from `InlineBannerIcon` (status symbols only via `StatusTone`), title, one-sentence explanation, optional detail, trailing recovery actions, optional Close, theme panel surface with bottom separator, one accessibility container named by the title | A new bespoke banner per feature; per-banner background, fonts, icon tint or control size |

## Reuse, never fork

One role has one implementation. Consistency comes from many surfaces sharing a single component, not from several copies that look alike today. A copy starts identical and drifts: one gets the theme-aware background, another does not; one gets the accessibility label, another does not; a fix lands in one and the others stay broken.

Forbidden:

- Copying an existing view, modifier or style into a new file or a `private struct`, then editing the copy. This includes "just for this screen" variants of a row, banner, badge, chip, header, card, field, empty state or section.
- Re-implementing in a view what a shared component or modifier already owns: background and material, corner radius, padding, fonts, separators, icon tint, status color.
- Patching a cloned copy alone when the bug belongs to the role. Fix the shared component, then migrate the clone onto it.
- Creating a component named after one feature when its role is generic (`GitConflictBanner` for what is an inline banner).

Required, in this order, before adding any `struct ...: View` or `ViewModifier`:

1. **Search.** Look for the role in this table, then grep sibling names (`Banner`, `Row`, `Badge`, `Chip`, `Header`, `Card`, `EmptyState`, `Field`, `Section`, `Notice`) and the files of related surfaces.
2. **Reuse as is.** Compose the existing component. Parameters and slots are the variation mechanism.
3. **Extend.** If it almost fits, add a parameter, slot or enum case to the shared component, in its own file, and check every consumer for regressions. Tone (success, warning, failure, neutral) is a semantic parameter, never a per-call color.
4. **Create once.** Only when no role fits: build one shared component in a shared file (not `private`, not in a feature file), name it by role, add a row to the table above and note it in `DESIGN_SYSTEM.md` in the same change. It must serve at least two surfaces or be the documented start of a role that will.

The change description states: roles searched, component reused or extended (source path), and for any new component, why no existing one fits. A new `struct ...: View` or `private struct` of a shared role with no such statement is rejected in review.

Subagents and parallel work: a delegate that builds UI receives the shared component paths and this section. Delegates do not create components in parallel. If one is needed, a single owner creates it first, and the others consume it. Shared component files have one owner at a time.

Worked example (2026-11-10): nine banners (large file, large-file mode, disk conflict, excluded build tag, merge conflict, Docker engine, OOM, run failure, commit editor) had each copied the same icon, title, message and actions skeleton. They drifted: one tinted its background, two aligned to the top, one named its close button differently, and only some had an accessibility label. All nine now compose `InlineBanner`; a new banner is a call to it, never a new skeleton. Gopilot transcript notices are a different role (a transcript row) and stay separate.

Every component implementation or change records:

1. Purpose, intended contexts, shared source path and consumers.
2. Inputs, identity, source of truth, scope and action effects.
3. Applicable states and transitions, including loading/error/stale/cancelled.
4. Feedback, recovery, draft preservation and undo semantics.
5. Pointer and keyboard behavior; focus acquisition/restoration; accessibility role/name/value.
6. Shared typography, spacing, colors and material roles; no arbitrary per-call-site styling.
7. Long content, narrow layout, Light/Dark and accessibility behavior on macOS 26+.
8. Evidence and intentional deviations from related components.

Do not redesign all consumers without assessing their behavior. A shared component fix requires checking affected consumers for regressions. New foundational components or tokens update this contract and the design system in the same change.

## Settings pane building blocks

| `SettingsNote` | Explanation or empty/blocked state inside a group, with an optional trailing recovery action | `.callout`, `.secondary`, optional SF Symbol; the action is a regular-size button. |
| `SettingsExplanation` | Privacy or policy text with a details popover | One or more `SettingsNote` paragraphs and a link-style details button that opens a popover. |
| `SettingsFieldRow` + `.settingsTextField()` | Editable string (URL, key, model ID, name, email) | Label leading, field column `SettingsMetrics.fieldWidth` wide, text left-aligned, `.roundedBorder`, help or validation below in `SettingsFieldHelp` (`.caption`, `.secondary`, optional symbol). Focus, submit and accessibility modifiers stay at the call site. |
| `SettingsValue` | Read-only value in a row | `.secondary`, monospaced digits. |
| `SettingsStatus` | State of a connection, machine, test or account | Busy (small progress view), or a symbol with a tone (`success` green, `warning` orange, `failure` red, `inactive` secondary); text is primary only when the tone carries meaning; optional `.caption` detail; one combined accessibility element. |
| `SettingsBadge` | Short tag on an item (Default, Bundled, capability tier) | `.caption2` medium on a `.quaternary` capsule; tint only for warning meaning. |
| `SettingsItemRow` | One object in a list group (account, toolchain, model route) | Optional 20pt icon, title with badges, `.caption` subtitle, trailing accessory (status, buttons, an `ellipsis.circle` menu). |
| `SettingsDrillDownRow` | A group with its own settings | 20pt tile, title, `SettingsValue`, chevron; opens a sub-page titled in the toolbar. |
| `SettingsActionRow` | Buttons that act on a group or pane | Leading actions (Import…, Export…, transient hint), trailing actions (Add…, Reset All). |
| `SettingsSearchField` | Filtering a table pane | Native `NSSearchField` above the table in the detail column, full table width, Esc clears. |

Spacing comes from `SettingsMetrics` (8pt rows, 4pt compact). Liquid Glass is only on the system sidebar and toolbar; the detail column is the standard grouped-form surface in every pane. Intentional difference: the Key Bindings table is bordered with alternating rows because it is a multi-column data table; list groups in forms (Ignored Files) stay a bordered list inside their section.
